# 性能与调度

## 实现

- 采购默认 8 个消费者,通知默认 4 个消费者,各自连续领取任务。
  一个慢订单只占一个采购槽,不会形成整批屏障或阻塞通知。
- 普通持久表 `orders`、`order_notifications` 使用 `FOR UPDATE SKIP LOCKED`、租约和
  令牌校验,支持多个进程共享队列。领取事务只持有数据库锁,网络请求在事务外执行。
- 就绪任务采用 `(next_run_at, id)` 部分索引;订单限定 next_run_at 非空,
  通知限定 sent_at 为空。保留原有索引以兼容其他查询。
- UNLOGGED 表 `upstream_cache` 缓存报价和上游余额,默认 TTL 分别为 2 秒和 1 秒。
  跨进程刷新租约和同进程请求合并降低集中刷新流量,刷新不占数据库连接等待网络。
  命中缓存不会延长原报价 TTL,等待余额期间报价已过期时会重新获取。
- 提交采购前后失效余额缓存,失效也撤销旧刷新令牌。旧请求返回的余额不能重新污染缓存。
  缓存只用于候选筛选,不保证上游仍有可用资金;成交结果始终读取上游原单。
- 商户限流使用普通表 `upstream_throttles`,每次 HTTP 请求和下单分别申请对应额度。
  TronBid 默认总请求 20 次/秒、创建订单 5 次/秒;TRONow 改用商户滚动窗口,默认 50/10。
  每进程每供应商默认 4 个 HTTP 并发槽;同商户多 key/实例共享额度和 Retry-After。
  详见 [TRONow 限流规范](upstream/tronow-errors.zh-CN.md)。
- 缓存按 Base URL、凭据和规格隔离,数据库仅保存摘要键,不保存 API 密钥。
  工作器每分钟清理过期缓存。查单、采购意图、订单、用户账本和通知均不使用 UNLOGGED。

UNLOGGED 数据在数据库异常重启后会被清空,也不会复制给备用服务器,因此这里仅用于可重建数据。
参见 [PostgreSQL UNLOGGED 说明](https://www.postgresql.org/docs/17/sql-createtable.html)。
SKIP LOCKED 是领取行时的锁策略,不是一种表类型;
[PostgreSQL 文档](https://www.postgresql.org/docs/17/sql-select.html#SQL-FOR-UPDATE-SHARE)
明确说明它适用于多个消费者访问队列的场景。

## 单上游直采说明

只配置一家供应商时,采购不调用报价/上游余额接口,报价缓存开关不会改变这一流程。
`benchmark_orders.py` 支持 `--mode single`（默认）和 `--mode multi`。
单上游基准会断言报价与余额请求均为 0;多上游基准使用模拟 TRONow 与 TronBid,
选择报价更低的 TronBid,用于继续验证比价与读缓存。
本轮分别以两种模式运行每组 20 单的模拟上游验证:所有组均完成 20 次采购和 20 次扣款;
单上游各组报价/余额请求均为 0,多上游保留这些请求并选中低价方。
单上游报价缓存不参与流程,组间耗时波动不能归因于报价缓存。

## 历史本地对照结果

以下数据记录于实现单上游直采之前,当时单个供应商仍会询价。
它不能作为当前单上游性能数据,也不能与当前两供应商基准直接等同比较。
2026-09-20,本机 Python 3.14 + uvloop、独立 PostgreSQL 17、回环 HTTP 模拟 TronBid。
每组预先入队 80 单,每个模拟 HTTP 请求等待 100ms;均验证 80 单采购和 80 次用户扣款,
无重复扣款。耗时从开始消费计到全部结算提交,不包含建库、迁移和入队准备时间。
P95 是这批同时入队订单的排队到结算时间,不是单个 HTTP 请求延迟。

| 配置 | 全部结算耗时 | 完成订单/秒 | 排队到结算 P95 | 报价请求 | 余额请求 | 采购请求 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| 并发 1,缓存关闭 | 18.263 秒 | 4.38 | 17.349 秒 | 80 | 80 | 80 |
| 并发 8,缓存关闭 | 6.762 秒 | 11.83 | 6.658 秒 | 80 | 80 | 80 |
| 并发 8,报价缓存 2 秒/余额缓存 1 秒 | 5.437 秒 | 14.71 | 5.332 秒 | 3 | 19 | 80 |

在该负载下,并发加缓存相对串行对照约 3.36 倍吞吐,报价/余额请求减少 86.25%。
串行对照是同一实现将并发设为 1 且关闭缓存,不是旧提交的独立生产压测。
基准将共享速率上限调到 1000/秒以观察本地调度能力,HTTP 并发仍为每供应商 4;
它不代表生产默认 5 单/秒限流下能达到 14.71 单/秒,也不代表真实上游或链上交付速度。

## 验证

上一轮并发优化验收的 187 项测试全部通过,覆盖多消费者不重复结算、慢采购不阻塞通知、通知按订单排序、
跨实例只刷新一次、刷新失败/取消恢复、缓存失效屏障、共享限流和 Retry-After。
Ruff、格式检查和 Pyright 通过。

另外在本次创建的独立 PostgreSQL 实例执行 immediate 停机后重启:
UNLOGGED 缓存确实清空,81 条订单、242 条资金流水、81 条采购尝试和 80 条通知均保留。
其中一笔尚未发送的采购意图、原始请求、租约和 4 TRX 冻结款保持完整。
这验证的是本地恢复场景,不是生产故障或主从切换的完整验收。

## 复现

先创建仅供基准使用的本机 PostgreSQL 空库,库名包含 `benchmark`。
设置 `ENERGY_BOT_BENCHMARK_DSN` 指向该库,然后执行:

```bash
uv run python scripts/benchmark_orders.py --mode single --orders 80 --delay-ms 100 --concurrency 8
uv run python scripts/benchmark_orders.py --mode multi --orders 80 --delay-ms 100 --concurrency 8
```

脚本仅允许回环地址,自动执行 Alembic 迁移,运行三组对照,输出 JSON 指标。
它会清空指定基准库内的业务表,必须使用专用测试库;不会读取真实 config.yaml,
也不会请求外部供应商。`--output` 可保存 JSON 结果。

## 部署与容量边界

先执行 `alembic upgrade head`,新增迁移 `ac2fb88df8cf` 建立缓存、共享限流和队列索引。
默认数据库连接池仍为常驻 5、最多 15;由于等待网络期间释放连接,无需直接按 HTTP
并发数扩大数据库连接池。增加实例时应核对实例总连接上限及上游商户配额。

`rental.order_concurrency` 和 `notification_concurrency` 是每进程上限,
`upstream_*_per_second` 是相同商户 scope 的共享速率;所有实例要使用相同配置。
TronBid 使用 rental 的平滑速率配置;TRONow 使用 upstream.tronow.request_limit/order_limit
滚动窗口配置,都应按各自平台实际配额设置。上表基准使用 TronBid 模拟接口,不代表
TRONow 50/10 限额下的实际性能。
`batch_size` 仅约束显式 tick/维护调用;生产消费者有任务时立即继续,空队列才等待
`idle_poll_seconds`。订单再次查单仍按 `poll_seconds` 调度。

多个实例消费数据库队列不要求多个实例同时管理 Telegram webhook;
部署时仍须统一 webhook 注册/注销与密钥,不能直接把单实例启动脚本当作滚动部署方案。
实际容量还取决于供应商配额、请求延迟、数据库硬件和活跃查单数量,需要部署环境验证。
