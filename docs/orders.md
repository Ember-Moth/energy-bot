# 余额订单系统

用户充值到经营者的钱包,平台用户账本与经营者在两家上游的预存余额相互独立。
当前账本和套餐销售价以 TRX 记账,精度 6 位小数。充值渠道、链上监听与兑换不属于本模块。

## 开启与使用

先执行 `alembic upgrade head`,配置上游 API 凭据,确保上游已经有可用余额。
在 `rental.products` 中填写真实销售套餐,再启用 `rental.enabled`。默认关闭,示例价格不会自动上架。
采购与通知使用独立的有界消费者池,随主程序启动,停止时取消在途请求并保留已提交的采购意图,重启后租约到期自动恢复。
不要通过关闭工作器来取消正在采购的订单。

仅在私聊中提供以下入口:

- `/rent`: 查看配置套餐与下单格式。
- `/rent 65000 TRON地址`: 按服务端套餐销售价下单;租期不给用户选择(产品约定只卖最短租期,
  用户拿到能量即使用),由套餐定义,同一能量数量只允许上架一个租期。
- `/balance`: 查看可用余额与冻结金额。
- `/deposit TRX数量`: 创建 TRX 充值单,回复收款地址与应付金额(GMPay 网关,见下文)。
- `/deposit_status 充值单号`: 查询充值单状态;回调延迟时主动查网关对账一次。
- `/orders`: 最近 20 条自己的订单。
- `/order 订单号`: 查询自己的订单状态与接收地址。
- `/cancel_order 订单号`: 只取消尚未提交上游的订单。采购结果不确定时拒绝取消。

Telegram 请求等待业务处理结束后才确认,不使用 aiogram 超时后提前返回 200 的包装。
同一 Telegram 消息以用户 + chat/message ID 去重,不能重复冻结余额。用户不能指定销售价。
Bot 先提交冻结及采购任务再发送受理回复,回复失败后的重投仍复用原订单。
程序接口 `rental.reserve_order()` 接受可信调用方提供的销售价、可选询价成本预算和稳定请求号;
相同请求号、不同订单参数会拒绝。调用方必须提交整个事务,异常时回滚。

## 用户余额

`wallet.credit(session, user_id=..., amount=Decimal(...), reference=...)` 是可信服务端入账接口。
调用者必须先独立验证充值凭证,保证 reference 是平台全局唯一的资金凭证,并在事务内调用。
同一凭证、用户和金额重放不重复入账,换用户或换金额则拒绝/事务冲突回滚。
Telegram 用户侧的充值入口是 `/deposit`(GMPay 网关),不是本接口;本接口仍供其他可信调用方使用。

### GMPay 充值(TRX)

`/deposit TRX数量` 创建充值单并向网关下单,回复收款地址与应付 TRX;
`currency="trx"` 时金额即 TRX 数量(网关 coin==base 短路,汇率 1),无折算环节。
支付成功回调到 `/payment/gmpay/notify`,验签、金额一致性校验后按
`reference = f"gmpay:{trade_id}"` 入账(与钱包幂等天然兼容);重复回调与并发投递
经 `upstream_deliveries` 永久去重。金额/币种不符不入账,充值单置 failed 转人工核对。
详细方案、epusdt 源码确证与防重放论证见 [GMPay 接入方案](gmpay-integration.md)。

- 下单: 可用余额减少、冻结金额增加,同时写 `hold:订单号` 流水。
- 上游确认成功: 冻结金额减少,写 `capture:订单号`,用户总余额才真正扣减。
- 未采购取消或全部供应商明确失败: 冻结金额退回可用余额,写 `release:订单号`。
- 超时、网关错误、未知响应、`REVIEWING`: 保留冻结款,不得直接解冻或创建替代采购。

订单行锁和钱包行锁串行化资金变动;订单状态、流水及采购结果在同一数据库事务提交。
流水业务键唯一,钱包余额有数据库非负约束。资金流水由服务追加,不修改既有条目。
已有非余额订单仍按旧路径处理,不会被自动计入新账本或自动提交采购。

## 单上游直采、多上游比价

按当前装配的上游数量自动选择流程,无需新增开关:

- **仅一家**: 跳过比价、询价和上游余额预查,本地检查已知规格后,持久化采购意图并直接下单。
  `quoted_cost` 记录为 NULL（未询价）,实际锁定成本仍从受理/查单结果记录。
- **两家**: 保留原来的并发询价、余额筛选和最低价选择。某次询价只成功一家,
  或失败切换后只剩一个候选,都不会变成免询价采购。
- **没有上游**: 无法采购,沿用有限等待后解冻的流程。

“装配”以凭据是否齐全为准:TRONow 需要 api_key + api_secret,TronBid 需要 api_key。
仅配置一家即可进入直采;环境变量覆盖也参与判断,不需要删除另一个客户端实现。
TRONow 仅支持 60 分钟租期,单上游直采也会在本地拦截其他租期并解冻,不会误买成 1 小时。
上游实际余额不足由采购接口拒绝;唯一供应商已明确失败/拒绝后解冻,不重新购买。

直采时 `max_cost_trx` 无法在采购前校验,只用于成交后的超预算记录;不会拿销售价冒充报价。
销售价固定,上游成交价高于预算时仍按原销售价扣用户余额。采购成本与利润差额由经营者承担。
幂等、有限重试、超时查单、冻结和结算规则不变。配置数量改变不会改写正在恢复的采购请求;
已有不确定结果的订单仍核对原供应商,不能通过增删配置换供应商重购。

## 多上游比价与采购恢复

并发向配置齐全的供应商询价并查询商户可用余额,只比较相同能量数量和租期。
TRONow 仅参与 60 分钟产品;TronBid 使用分钟租期,采购固定 `payment_mode=balance`。
剔除余额不足、不可用、过期报价、超过预算和本订单已明确失败的供应商,选择最低报价。
无可采购报价会有限次重试,耗尽后解冻。销售价与采购成本分别存储。

**多上游询价预算不是上游锁价保证。** `max_cost_trx` 默认等于销售价,限制的是提交前报价。
TRONow 在下单受理时重新锁价,接口不支持传最大成交价。成交价超过预算时记录
`COST_OVERRUN` 并写告警日志,继续跟踪原订单,不追加用户扣款,也不另开新单。
报价与实际成交之间的价差由经营者承担。启用前应留足利润空间。

每次采购先在 `purchase_attempts` 保存供应商、报价、稳定业务号、幂等键和精确 JSON 文本,
数据库提交后才发送 POST。后台租约与令牌防止过期工作器覆盖后续结果。

- 已知上游单号: 仅 GET 查原单,不重新 POST。
- TRONow 不知道单号: 先按业务号查单,明确 `ORDER_NOT_FOUND` 后重放原幂等键与原字节。
- TronBid 不知道单号: 协议无业务号查询,以原幂等键和原字节重放,不能换键或换供应商。
- 明确首次提交被拒绝,或原采购已确认失败: 保留失败尝试,下一轮重新询价并选剩余供应商。
- 恢复阶段出现鉴权/冲突等错误: 不把错误当原单失败;保留资金并标记待核对。
- `REVIEWING` / 身份或锁定金额不一致: 通知用户并写告警日志,只允许继续核对原单。
  已有单号继续查询;没有单号且不能证明安全时等待人工从上游核实,不自动重复购买。

TRONow 签名回调对余额订单的作用是持久化唤醒查单;最终结算使用完整订单查询结果。
回调先于 POST 响应到达时可以按业务号定位采购意图。旧订单保留原有回调处理方式。

业务不管理上游租期:用户拿到能量即使用,能量到账(delegating → active)即为成功终态,
不再跟踪或展示租期到期时间;上游在租期结束后物理回收能量,与本地订单状态无关。
TronBid 若首次查询已是 `expired`(余额支付模式下视为异常),无法证明交付,
保留冻结款并转核对,不自动退款或重购。

## 通知与运维

成功、解冻和待核对事件写入通知表,由后台任务重试发送。发送失败不影响已提交资金结算。
通知是至少一次投递:发送后、标记完成前崩溃可能重复消息,但不会重复扣款。
日志包含本地订单号,不输出 API 凭据、签名或原始错误响应。
`last_error` 和各次采购记录供人工核对,不得靠直接改状态或清空上游单号绕过恢复流程。

## 验证边界

本地测试使用独立 PostgreSQL 和回环模拟上游,覆盖资金守恒、并发冻结、最低价选择、
分钟产品、超时/崩溃恢复、失败切换、人工核对、重复结算与通知重试。
这不代表真实上游商户配置、回调时间戳单位、库存、链上到账及付费验收已通过。


## 并发调度与缓存

`orders` 的调度字段和 `order_notifications` 是普通持久表队列,采用
`FOR UPDATE SKIP LOCKED` 领取,短事务提交租约后才访问外部网络。每个消费者完成后立即
取下一项,没有整批等待最慢订单的屏障。通知按订单保持先后顺序,不同订单可并行发送。
有效任务集合有独立部分索引,完成任务不会持续挤占就绪索引。

`upstream_cache` 为 UNLOGGED 表,仅缓存报价和上游余额。跨进程刷新租约防止集中刷新,
同进程还会合并相同读取。缓存失效后旧刷新令牌无法写回;采购前后失效余额缓存。
上游查单、采购结果、冻结和资金流水从不使用缓存。缓存丢失后按需重建。
报价有效期不会因命中缓存延长,TronBid 的报价 TTL 不超过供应商给出的有效秒数。

每个 HTTP 请求在生成签名前申请共享商户额度,订单和地址激活 POST 同时消耗创建额度。
429 的 `Retry-After` 会传播到同商户其他实例。长等待退回持久任务,避免占住工作器。
工作器只在短事务中持有数据库连接;等待限流、上游或 Telegram 时不占连接。
详见 [性能与调度](performance.md)。


无上游单号的采购尝试有 max_submit_attempts 自动提交/恢复预算,耗尽后只核对原单,
保留冻结款,不直接退款或换单。等待采用不短于 Retry-After 的退避与随机抖动。
最近一次原 HTTP 状态、request_id、原 code 保存在采购尝试中,不根据 message 判断结果。
TRONow 仅 HTTP 404 + ORDER_NOT_FOUND 可以作为按业务号未找到订单的证据;
其他状态即使携带同名 code 也不能触发重新提交。完整错误语义见上游文档。
